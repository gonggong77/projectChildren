| 항목 | 내용 |
|---|---|
| 문서 버전 | v1.0 (초안) |
| 작성일 | 2026-07-24 |
| 대상 릴리스 | MVP (1차 출시) |

## 1. 제품 개요

### 1.1 한 줄 정의
전국의 **어린이 관람 가능 공연**을 한 곳에서 검색하고, 공연 상세 정보와 함께 **공연장 주변 어린이 놀이시설**까지 지도로 확인할 수 있는 웹서비스.

### 1.2 왜 이 제품인가
부모의 실제 의사결정 단위는 "공연 티켓"이 아니라 **"아이와 함께하는 반나절 외출"**이다. 그런데 공연 정보(KOPIS/예매처)와 놀이·휴식 공간 정보(지자체·행안부 데이터)는 완전히 분리된 채 제공된다. 이 제품은 두 데이터를 **공연장 좌표**라는 축으로 결합해, 부모가 여러 사이트를 오가지 않고 하루 동선을 한 화면에서 그릴 수 있게 한다.

### 1.3 차별점
- 기존 예매 플랫폼: 공연 판매가 목적 → 연령·러닝타임·수유실 같은 **부모 관점 정보가 파편적**
- 지도 서비스: 놀이터는 나오지만 **공연과 연결되지 않음**
- 본 제품: `공연 → 공연장 좌표 → 반경 내 놀이시설`을 하나의 흐름으로 제공

### 1.4 제품 원칙
1. **로그인 없이 즉시 사용** — 가입 장벽 없이 검색부터 즐겨찾기까지 완결
2. **부모가 판단할 정보만** — 관람연령, 러닝타임, 가격, 수유실/주차 여부를 상위에 배치
3. **예매는 위임** — 결제·예매는 하지 않고 공식 예매처로 연결 (법적·운영 리스크 회피)
4. **모바일 우선** — 이동 중 확인이 주 사용 맥락

## 2. 대상 사용자

### 2.1 주 사용자 (Primary)
**만 3~9세 자녀를 둔 부모 (30~40대, 모바일 이용 비중 높음)**

| 페르소나 | 상황 | 니즈 |
|---|---|---|
| 주말 나들이 기획자 (주 타깃) | 주말에 아이와 뭘 할지 금요일 밤에 검색 | 우리 동네에서 이번 주말에 볼 만한 공연 + 공연 전후로 들를 곳 |
| 원정 관람형 | 아이가 좋아하는 특정 공연을 위해 타 지역 이동 | 낯선 지역이라 공연장 주변 정보가 전혀 없음 |
| 조부모·보호자 | 아이를 데리고 외출 | 큰 글씨, 단순한 흐름, 전화 연결 |

### 2.2 부 사용자 (Secondary)
- 어린이집·유치원 교사 (단체 관람 후보 탐색)
- 지역 육아 커뮤니티 운영자 (정보 공유용)

> 부 사용자는 MVP에서 별도 기능을 제공하지 않으며, 주 사용자용 화면을 그대로 사용한다.

## 3. 문제 정의

### 3.1 현재 사용자 여정과 이탈 지점

```
[1] "이번 주말 아이랑 볼 공연 없나?"
     → 포털 검색 → 예매처 3~4곳을 각각 방문 (인터파크/티켓링크/대학로티켓…)
     → 사이트마다 '아동' 분류 기준이 달라 누락 발생          ❌ 문제 1

[2] 공연 하나를 고름
     → 관람연령·러닝타임·좌석 정보가 페이지마다 흩어져 있음   ❌ 문제 2

[3] "공연장 근처에서 밥 먹고 좀 놀다 올까?"
     → 지도 앱으로 전환 → '놀이터' 검색 → 정보 신뢰도 낮음    ❌ 문제 3

[4] 다음 주에 다시 보려니 어디서 봤는지 기억 안 남           ❌ 문제 4
```

### 3.2 문제 정리

| # | 문제 | 근본 원인 | MVP 대응 |
|---|---|---|---|
| P1 | 어린이 공연 정보가 예매처별로 흩어져 있음 | 통합 뷰 부재 | KOPIS 공연목록 API `kidstate=Y` 기반 전국 단일 목록 |
| P2 | 부모가 필요한 판단 정보(연령/시간/가격/편의시설)를 모으기 어려움 | 예매 중심 UI | 공연 상세 + 공연시설 상세를 병합해 한 화면 제공 |
| P3 | 공연장 주변 아이와 갈 곳을 따로 찾아야 함 | 데이터 도메인 분리 | 공연장 좌표 기준 반경 내 놀이시설 목록·지도 |
| P4 | 관심 공연을 다시 찾기 어려움 | 저장 수단 없음 | localStorage 기반 즐겨찾기 (로그인 불필요) |

### 3.3 문제 아님 (의도적 비대응)
- 티켓 최저가 비교 → 데이터 부재, 예매처 정책 이슈
- 실시간 잔여 좌석 → API 미제공
- 공연 후기·평점 → UGC 운영 부담 (2차 릴리스 검토)

## 4. 주요 기능

### F1. 어린이 공연 검색 및 목록

| 항목 | 내용 |
|---|---|
| 설명 | 어린이 관람 가능 공연을 포스터 카드 그리드로 제공 |
| 검색 | 공연명 키워드 (부분 일치, 대소문자·공백 무시) |
| 필터 | 지역(시도 → 구군 2단계), 공연 기간, 공연상태(공연예정/공연중) |
| 정렬 | 공연 시작일 임박순(기본), 공연명순 |
| 페이징 | 무한 스크롤 대신 **"더 보기" 버튼** (스크롤 위치 복원 문제 회피, 20건 단위) |
| 카드 노출 정보 | 포스터, 공연명, 공연기간, 공연시설명, 지역, 공연상태 배지, 즐겨찾기 하트 |
| 빈 상태 | "조건에 맞는 공연이 없어요" + 필터 초기화 버튼 |

**어린이 공연 판별 기준 (중요)**
KOPIS 공연목록 조회의 `kidstate=Y` 파라미터를 1차 기준으로 사용한다. 단, 이 값은 KOPIS 등록 시점의 분류에 의존하므로 **누락 위험**이 있다. → 8.5절 설계 의사결정 D3 참조.

---

### F2. 지역 필터

- KOPIS 공통코드의 **행정표준코드 기반** 시도(2자리)·구군(4자리) 코드를 그대로 사용
  - 시도 예: `11` 서울특별시, `26` 부산광역시, `41` 경기도, `51` 강원특별자치도
  - 구군 예: `1111` 종로구, `1168` 강남구
- 구군 셀렉트는 시도 선택 시 동적으로 채워짐 (`/api/regions` 응답 활용)
- 선택 상태는 URL 쿼리스트링에 반영 → **공유·새로고침·뒤로가기 시 유지** (MVP 필수)

### F3. 공연 상세 보기

KOPIS **공연 상세 조회**(`/openApi/restful/pblprfr/{mt20id}`)와 **공연시설 상세 조회**(`/openApi/restful/prfplc/{mt10id}`) 두 응답을 서버에서 병합해 제공한다.

**노출 필드 (부모 의사결정 기준으로 선별)**

| 블록 | 표시 항목 | KOPIS 필드 | 선정 사유 |
|---|---|---|---|
| **헤더** | 포스터 | `poster` | 아이와 함께 고를 때 1차 판단 근거 |
| | 공연명 / 장르 / 공연상태 | `prfnm` / `genrenm` / `prfstate` | |
| **관람 핵심** ★ | **관람 연령** | `prfage` | 부모의 1순위 필터 조건 |
| | **러닝타임** | `prfruntime` | 아이 집중력·낮잠 시간과 직결 |
| | **티켓 가격** | `pcseguidance` | 예산 판단 |
| | 공연 기간 | `prfpdfrom` ~ `prfpdto` | |
| | 공연 시간 | `dtguidance` | 요일별 회차 확인 |
| **공연장** | 공연시설명 / 공연장명 | `fcltynm` / `prfplcnm` | |
| | 주소 | `adres` (시설 상세) | |
| | 전화번호 | `telno` (시설 상세) | 문의·현장 확인 |
| | **편의시설 배지** ★ | `suyu`(수유실), `nolibang`(놀이방), `parkinglot`(주차), `restaurant`, `cafe`, `store` | **영유아 동반 시 결정적 정보. 경쟁 서비스가 노출하지 않는 항목** |
| | 무장애 시설 | `elevbarrier`, `parkbarrier`, `restbarrier`, `runwbarrier` | 유모차 동반 접근성 |
| **예매** | 예매처명 + 링크 | `relates > relatenm`, `relateurl` | 외부 탭으로 이동 (결제 미구현) |
| **소개** | 줄거리 | `sty` | 접기/펼치기 |
| | 소개 이미지 | `styurls > styurl` | 가로 스크롤 썸네일 |
| | 출연진 | `prfcast` | 보조 정보 |
| **위치** | 지도 (Leaflet) | `la`, `lo` (시설 상세) | F4 |
| **주변** | 인근 놀이시설 목록 | 놀이시설 API | F5 |

**MVP에서 제외한 KOPIS 필드**: `prfcrew`(제작진), `entrpsnm*`(기획/제작사 5종), `musicallicense`, `musicalcreate`, `festival`, `daehakro`, `visit`, `frstregdt`, `updatedate`
→ 사유: 부모의 관람 의사결정에 기여하지 않음. `updatedate`는 화면에는 미노출하되 **DB에는 저장**(증분 수집 및 데이터 신선도 판단용).

### F4. 지도 표시 (Leaflet)

- 공연장 좌표(`la`, `lo`)를 중심으로 지도 렌더링, 기본 줌 레벨 15
- 마커 2종 구분
  - 🎭 공연장 (1개, 강조 스타일)
  - 🛝 놀이시설 (반경 내 최대 20개)
- 놀이시설 마커 클릭 → 하단 목록의 해당 항목으로 스크롤 + 아코디언 자동 확장 (**지도 ↔ 목록 양방향 연동**)
- 타일: OpenStreetMap 표준 타일 (출처 표기 필수). 상용 트래픽 발생 시 타일 제공처 정책 재검토 → 9.3 리스크 참조
- 좌표가 없는 공연장은 지도 영역 대신 "위치 정보가 제공되지 않는 공연장입니다" 안내 + 주소 텍스트만 노출 (**Graceful degradation**)

---

### F5. 인근 어린이 놀이시설 목록 (핵심 차별 기능)

**동작**
1. 공연장 좌표 기준 **반경 1km(기본)** 내 놀이시설을 거리순으로 조회 (최대 20건)
2. 결과 0건이면 자동으로 반경 3km로 1회 확대 재조회 후, 그래도 없으면 빈 상태 안내
3. 목록은 **아코디언(1행 = 1시설)**, 기본은 접힌 상태

**접힌 상태 표시**: 놀이시설명 / 설치장소 유형 배지 / 공연장으로부터 거리(m)

**펼친 상태 표시 (필수 정보만)**

| 항목 | 근거 필드 | 비고 |
|---|---|---|
| 놀이시설명 | `pfctNm` | |
| 설치장소 유형 | `instlPlaceCd` → 라벨 변환 | 예: A003 도시공원, A010 주택단지, A030 자연휴양림 |
| 도로명주소 | 주소 필드 | 지번주소는 fallback |
| 물놀이형 놀이기구 여부 | `wowaStylRideCd` (X001 포함 / X002 미포함) | 여름철 방문 판단에 유용 |
| 실내/실외 구분 | 제공 시 노출 | 우천 시 대안 판단 |
| 공연장으로부터 거리 | 서버 계산값 | "도보 약 N분" 병기 (직선거리 ÷ 67m/분, 근사치 명시) |
| 액션 | — | [지도에서 보기] |

> **⚠️ 제품 판단 — 표시할 놀이시설의 범위**
> 행안부 데이터는 「어린이놀이시설 안전관리법」상 **관리 대상 전체**이며, `A010:주택단지`, `A006:어린이집`, `A007:유치원`처럼 **외부인이 이용할 수 없는 시설이 다수 포함**된다. 이를 그대로 노출하면 "가봤더니 아파트 단지 안이라 못 들어갔다"는 최악의 사용자 경험이 발생한다. → 8.5절 설계 의사결정 D4에서 대안 비교.

### F6. 즐겨찾기 (localStorage)

- 목록 카드·상세 화면의 하트 아이콘으로 추가/삭제 (토글, 낙관적 업데이트)
- 저장 키: `kidsstage:favorites` / 값: 공연 ID(`mt20id`) 배열 + 저장 시각
- 즐겨찾기 목록 화면에서 서버에 ID 배열을 전달해 최신 공연 정보를 재조회
  → **저장 시점의 스냅샷이 아니라 항상 최신 상태 표시** (공연 종료 시 "공연완료" 배지)
- 삭제된 공연 ID는 조회 실패 시 목록에서 자동 정리 + 토스트 안내
- 브라우저·기기 간 동기화 없음을 **설정 화면에 1줄로 명시** (로그인 미제공에 따른 한계)

## 5. 화면 구성

### 5.1 화면 목록 및 라우팅

| # | 화면 | 경로 | 설명 |
|---|---|---|---|
| S1 | 공연 목록 (홈) | `/?sido=11&gugun=1168&q=...&page=1` | 검색·필터·카드 그리드 |
| S2 | 공연 상세 | `/performances/:mt20id` | 상세 + 지도 + 인근 놀이시설 |
| S3 | 즐겨찾기 | `/favorites` | 저장한 공연 목록 |
| S4 | 404 / 오류 | `*` | 공통 오류 화면 |

전역 요소: 상단 헤더(로고, 즐겨찾기 진입), 하단 푸터(데이터 출처 표기)

## 8. 기술 고려사항

### 8.1 아키텍처

```
┌──────────────┐    ┌──────────────────────────┐    ┌────────────────┐
│  React (SPA) │───▶│      FastAPI 서버         │───▶│  SQLite (.db)  │
│  + Leaflet   │◀───│  /api/*  (읽기 전용)      │◀───│  읽기 전용 조회 │
└──────────────┘    └──────────────────────────┘    └────────────────┘
       │                        ▲
  localStorage                  │ (배치, 스케줄 실행)
   (즐겨찾기)          ┌────────┴────────┐
                      │ Ingestion Worker │──▶ KOPIS OpenAPI (XML)
                      │  (동일 코드베이스)│──▶ 행안부 놀이시설 API (JSON)
                      └──────────────────┘
```

**원칙**: 프론트엔드는 외부 API를 직접 호출하지 않는다. 서비스 키가 브라우저에 노출되지 않으며, CORS·XML 파싱·Rate Limit을 서버가 전담한다. 사용자 요청 경로에는 외부 API 호출이 **없다**(전량 사전 적재) → 응답 속도와 외부 장애 격리를 동시에 확보.

### 8.2 기술 스택

| 레이어 | 선택 | 비고 |
|---|---|---|
| 프론트엔드 | React 19.x + Vite | React는 2026년 7월 기준 19.2.x 계열이 최신 안정 라인. `package.json`에 마이너 버전까지 고정하고 lockfile 커밋 |
| 라우팅 | React Router | 3개 화면 수준이라 별도 프레임워크 불필요 |
| 서버 상태 | TanStack Query | 캐싱·재시도·로딩 상태 표준화. 미도입 시 fetch 래퍼 훅으로 대체 가능 |
| 지도 | Leaflet + react-leaflet | OSM 타일, 출처 표기 |
| 백엔드 | FastAPI + Uvicorn | Pydantic 모델로 응답 스키마 고정, `/docs` 자동 생성 |
| DB | SQLite (WAL 모드) | 읽기 위주 워크로드, 단일 파일 배포 |
| 배치 | Python 스크립트 (`ingest.py`) + cron/APScheduler | 8.5-D5 참조 |
| HTTP 클라이언트 | httpx (async) | 재시도·타임아웃 정책 통일 |
| 파서 | `xml.etree` 또는 lxml (KOPIS는 XML 응답) | 놀이시설 API는 JSON |

### 8.3 외부 데이터 소스 명세

**(1) KOPIS 공연예술통합전산망 OpenAPI** — 인증 파라미터명 `service`, 응답 XML

| 용도 | 엔드포인트 | 주요 파라미터 | 제약 |
|---|---|---|---|
| 공연 목록 | `/openApi/restful/pblprfr` | `stdate`, `eddate`, `cpage`, `rows`, `kidstate=Y`, `signgucode`, `signgucodesub`, `afterdate` | **조회 기간 최대 31일**, `rows` **최대 100건** |
| 공연 상세 | `/openApi/restful/pblprfr/{mt20id}` | `service` | 공연 1건당 1회 호출 |
| 공연시설 상세 | `/openApi/restful/prfplc/{mt10id}` | `service` | **좌표(`la`,`lo`) 확보 경로** |
| 공연시설 목록 | `/openApi/restful/prfplc` | `cpage`, `rows`, `signgucode` | 공연장 사전 적재용 |

> ⚠️ **문서 정합성 이슈**: 개발가이드 4.1의 서비스 URL은 `/openApi/restful/pblprfr/{공연시설아이디}`로 적혀 있으나, 4.2의 요청 예제는 `/openApi/restful/prfplc/FC001247`이다. **예제(prfplc) 기준으로 구현**하고 개발 착수 시 1건 실호출로 검증한다.

**(2) 행정안전부 전국어린이놀이시설정보서비스**
- 요청 주소: `http://apis.data.go.kr/1741000/pfc3/getPfctInfo3`, 응답 JSON, 인증 파라미터명 `serviceKey`
- 요청 파라미터: `serviceKey`, `pageIndex`, `recordCountPerPage`(필수), `instlPlaceCd`, `pfctNm`, `pfctSn`, `wowaStylRideCd`
- 트래픽: **개발계정 일 10,000건** (운영계정은 활용사례 등록 시 증량 신청 가능)
- **제약**: 지역(시도/구군) 필터 파라미터가 없어 **전국 전량 적재 후 서버에서 공간 필터링**해야 한다
- **미검증 항목**: 응답에 위도/경도 필드가 포함되는지 Swagger 명세로 확인 필요 → 8.5-D2

### 8.4 서버 API 설계 (FastAPI)

| Method | Path | 설명 | 주요 파라미터 |

| GET | `/api/performances/{mt20id}` | 공연 상세(+공연장 병합) | — |

### 8.5 주요 설계 의사결정 (대안 비교)

#### D1. 인근 놀이시설 공간 검색 방식

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. Bounding Box + Python Haversine** | 위경도 ±Δ로 SQL 1차 필터 → 앱 레이어에서 정확 거리 계산·정렬 | 추가 의존성 0, 구현 30분, 디버깅 쉬움 | 후보군이 크면 CPU/메모리 부담 |
| **B. SQLite R*Tree 인덱스 + Haversine 재정렬** | R*Tree 가상 테이블로 공간 인덱싱 | SQLite 표준 확장이라 별도 설치 불필요, 수만~수십만 건에서 안정적 | 인덱스 테이블 동기화 로직 추가 |
| **C. 공연장별 사전 계산 테이블** | 배치 시 `venue_id × playground_id × 거리`를 미리 저장 | 조회 O(1), 응답 최속 | 반경 변경 시 전면 재계산, 저장 공간 증가, 데이터 갱신 지연 |

> **권장: A안으로 시작 → 놀이시설 5만 건 초과 또는 p95 응답 300ms 초과 시 B안으로 전환.**
> 근거: MVP의 조회 트래픽은 낮고 공연장 수는 제한적(KOPIS 공연장 코드 기준 수천 개)이라 A안의 비용이 사실상 발생하지 않는다. C안은 "반경 토글"(6.2 Should) 요구와 충돌하므로 MVP에서 부적합.

#### D2. 놀이시설 좌표 확보 방안

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. API 응답의 좌표 필드 사용** | `getPfctInfo3` 응답에 위경도가 있으면 그대로 저장 | 추가 작업 없음, 원본 정합성 | **제공 여부 미확인** (포털 설명은 주소 항목 중심) |
| **B. 주소 → 좌표 지오코딩** | 도로명주소 API / 카카오·네이버 지오코딩으로 변환 후 저장 | 좌표 없어도 확보 가능 | 별도 키 발급, 건수만큼 호출(전국 수만 건), 주소 표기 오류 시 실패 |
| **C. 표준데이터 파일(CSV) 병합** | `전국어린이놀이시설표준데이터` 파일데이터를 1회 다운로드해 좌표 컬럼 병합 | 대량 확보에 트래픽 소모 없음, 무료 | 갱신 주기 수동, API와 키(시설번호) 매칭 검증 필요 |

> **권장: A → C → B 순의 폴백 전략.**
> 착수 첫날 A를 실호출로 검증하고, 없으면 C로 대량 확보 후 매칭 실패분만 B로 보완한다. 좌표가 끝내 없는 시설은 **목록에서 제외**한다(거리 계산 불가 = 제품 가치 없음).

#### D3. "어린이 공연" 판별 기준

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. `kidstate=Y` 단독** | KOPIS 목록 API의 아동공연 플래그만 사용 | 구현 최단, 데이터 제공기관 기준을 따름 | 등록자가 체크하지 않은 공연 누락 |
| **B. `prfage` 파싱 병행** | 상세의 관람연령을 파싱해 "만 N세 이상, N≤7" 조건 추가 | 재현율(recall) 상승 | 표기가 자유 텍스트("전체관람가", "48개월 이상")라 파싱 규칙 유지비 발생 |
| **C. 장르+키워드 휴리스틱** | 아동 장르·제목 키워드(인형극, 뮤지컬 등)로 확장 | 최대 커버리지 | **오탐 위험**(성인 공연 노출)이 크며 서비스 신뢰도 훼손 |

> **권장: MVP는 A안. 단, 수집 시 `prfage`를 정규화해 별도 컬럼에 저장**해두고, 출시 후 A와 B의 차집합 규모를 측정해 B 도입을 판단한다. C는 오탐 비용이 편익을 초과하므로 채택하지 않는다.

#### D4. 노출할 놀이시설의 범위 (설치장소 필터)

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. 전량 노출** | 반경 내 모든 시설 표시 | 구현 최단, 결과 건수 많음 | 아파트 단지·어린이집 등 **출입 불가 시설**이 대부분을 차지해 신뢰 하락 |
| **B. 공공 이용 가능 장소 화이트리스트** | `A003 도시공원`, `A030 자연휴양림`, `A031 하천`, `A032 야영장`, `A033 공공도서관`, `A092 육아종합지원센터` 등만 노출 | 실제로 갈 수 있는 곳만 남아 **정보 신뢰도 최상** | 지역에 따라 결과 0건 가능 |
| **C. 전량 노출 + 이용 가능성 배지** | "공공 개방 / 단지 내 제한" 배지 병기 | 정보량과 정확성 절충 | 개방 여부는 추정값이라 오안내 리스크, UI 복잡도 증가 |

> **권장: B안(화이트리스트)을 기본값으로 적용하고, 0건일 때만 "주변 다른 놀이시설도 보기" 링크로 A안 결과를 노출한다.**
> 근거: 제품 원칙 2("부모가 판단할 정보만")에 부합하며, 한 번의 헛걸음이 재방문율에 치명적인 오프라인 연계 서비스 특성상 정밀도(precision)를 재현율보다 우선한다.

#### D5. 데이터 수집 주기 전략

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. 매일 전체 재적재** | 오늘~+90일을 31일 단위로 3회 분할 조회 | 로직 단순, 상태 불일치 없음 | 호출량 많음, 적재 중 일시적 불일치 |
| **B. `afterdate` 증분 + 주 1회 전체** | 변경분만 수집하고 주간 전체 동기화 | 호출량 최소, 최신성 유지 | 삭제된 공연 감지 로직 별도 필요 |
| **C. 요청 시 실시간 프록시 + 캐시** | 사용자 요청 시 호출 후 TTL 캐시 | 항상 최신 | 첫 응답 지연, 외부 장애가 곧 서비스 장애, 요구사항(사전 적재)과 불일치 |

> **권장: MVP는 A안(1일 1회, 새벽 4시). 운영 안정화 후 B안으로 전환.**
> 놀이시설 데이터는 변경 빈도가 낮으므로 **주 1회 전량 재적재**로 분리한다. C안은 "서버가 API를 호출해 SQLite에 저장 후 사용"이라는 요구사항에 위배된다.

```sql
-- 공연
CREATE TABLE performances (

  openrun       TEXT,  child       TEXT,

);

CREATE TABLE performance_relates (   -- 예매처 (1:N)
  mt20id TEXT, relatenm TEXT, relateurl TEXT, sort_no INTEGER

CREATE TABLE performance_images (    -- 소개 이미지 (1:N)
  mt20id TEXT, styurl TEXT, sort_no INTEGER

-- 공연시설
CREATE TABLE venues (
  mt10id TEXT PRIMARY KEY,
  fcltynm TEXT, adres TEXT, telno TEXT, relateurl TEXT,
  la REAL, lo REAL,                       -- 좌표 (지도·거리 계산의 기준)
  parkinglot TEXT, restaurant TEXT, cafe TEXT, store TEXT,
  nolibang TEXT, suyu TEXT,               -- 영유아 편의시설
  parkbarrier TEXT, restbarrier TEXT, runwbarrier TEXT, elevbarrier TEXT,
  seatscale INTEGER, sidonm TEXT, gugunnm TEXT
);

-- 놀이시설
CREATE TABLE playgrounds (
  pfct_sn TEXT PRIMARY KEY,               -- 놀이시설번호
  pfct_nm TEXT NOT NULL,
  instl_place_cd TEXT, instl_place_nm TEXT,
  road_addr TEXT, lotno_addr TEXT, zip TEXT,
  lat REAL, lng REAL,
  wowa_styl_ride_cd TEXT,                 -- 물놀이형 포함 여부
  indoor_yn TEXT,
  is_public_access INTEGER,               -- D4 화이트리스트 플래그
  updated_at TEXT
);
CREATE INDEX idx_pg_bbox ON playgrounds(lat, lng);
CREATE INDEX idx_perf_search ON performances(signgucode, prfpdfrom, prfpdto, prfstate);

-- 적재 이력 (운영 관측용, 관리자 화면 대체)
CREATE TABLE ingest_logs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  source TEXT, started_at TEXT, finished_at TEXT,
  fetched INTEGER, upserted INTEGER, failed INTEGER, message TEXT
);
```

## 9. 완료 기준 (Definition of Done)

### 9.1 기능 수용 기준 (전 항목 통과 시 MVP 출시)

| # | 시나리오 | 기대 결과 |
|---|---|---|
| AC-1 | 홈에서 "공룡"을 검색한다 | 공연명에 해당 키워드를 포함한 어린이 공연 목록이 포스터와 함께 표시된다 |
| AC-2 | 시도 "서울특별시", 구군 "강남구"를 선택한다 | 해당 지역 공연만 표시되고, 새로고침 후에도 필터가 유지된다 |
| AC-3 | 목록에서 공연 카드를 클릭한다 | 상세 화면으로 이동해 포스터·관람연령·러닝타임·가격·공연시간·공연장 정보·예매처 링크가 표시된다 |
| AC-4 | 상세 화면을 스크롤한다 | 공연장 위치가 지도에 마커로 표시된다 |
| AC-5 | 지도 아래를 확인한다 | 반경 내 놀이시설이 **거리순**으로 목록에 표시된다 |
| AC-6 | 놀이시설 항목 하나를 클릭한다 | 해당 칸이 확장되고 다른 칸은 접힌다 |
| AC-7 | 확장된 칸을 확인한다 | 시설명·설치장소·주소·물놀이형 여부·거리가 표시된다 |
| AC-8 | 공연 카드/상세의 하트를 누른다 | 즐겨찾기에 추가되고, 브라우저를 껐다 켜도 `/favorites`에서 조회된다 |
| AC-9 | 즐겨찾기에서 하트를 다시 누른다 | 목록에서 즉시 제거되고 재방문 시에도 제거 상태가 유지된다 |
| AC-10 | 좌표가 없는 공연장의 상세를 연다 | 지도·놀이시설 섹션이 안내 문구로 대체되고, 나머지 정보는 정상 표시된다 |
| AC-11 | 배치 스크립트를 실행한다 | 공연·공연장·놀이시설이 SQLite에 적재되고 `ingest_logs`에 결과가 기록된다 |
| AC-12 | 브라우저 네트워크 탭을 확인한다 | 외부 API(KOPIS/공공데이터포털) 직접 호출이 **0건**이며, 서비스 키가 노출되지 않는다 |

> AC-1~AC-7은 사용자가 제시한 성공 기준 1~5에 대응하며, AC-8~AC-9는 성공 기준 6(추가 개발 완료 시)에 대응한다.
